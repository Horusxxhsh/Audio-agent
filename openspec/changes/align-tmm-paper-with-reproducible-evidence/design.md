## 上下文

当前论文已形成较完整叙事，但“数字证据链”存在断裂：
- 一部分核心结论依赖缺失的历史全向量工件，无法由当前仓库重放；
- 同名指标（L2）在不同章节对应不同尺度，读者无法进行公平横向比较；
- 数据规模与拆分口径不一致（总数据、测试子集、知识库规模混述）；
- supplementary 与主文的层选择结果和样本数存在冲突。

该问题不是算法实现问题，而是论文证据治理问题。目标是在“不新增实验、不更改既有实验结论来源”的前提下，形成可审计、可复算、可维护的稿件事实层。

## 目标 / 非目标

**目标：**
- 建立“论文数字 -> 仓库工件”的一一映射机制（Claim -> Evidence）。
- 统一全文对数据规模、指标定义、指标尺度、实验子集的描述口径。
- 对不可复现数字执行规范化处置（删除/定性降级/Future Work）。
- 收敛主文与 supplementary 的冲突陈述。

**非目标：**
- 不新增或重跑实验。
- 不修改核心算法实现（TRR/Fusion/LLM/约束修复逻辑）。
- 不引入新的外部数据依赖。

## 决策

### 决策 1：采用“证据优先”的结果治理模型

- 规则：论文中的关键量化结论必须可追溯到仓库内稳定工件（CSV、报告、原始评分数据、脚本定义）。
- 输出形态：维护一个可读的 Claim -> Evidence 对照（可在 design/spec/tasks 中体现），作为审稿阶段核对基线。
- 理由：相比“补实验”路径，此方案与当前约束（实验已结束）一致，且能立即降低学术诚信风险。

**备选方案**
- 方案 A：保留现有数字，仅做文字润色。否决，无法解决可复现性风险。
- 方案 B：补齐缺失工件并重算全部表格。否决，超出当前时间与流程约束。

### 决策 2：把“可复现口径”显式落到 capability 级规范

- 新增 capability：`paper-evidence-traceability`，用于约束跨章节的一致性规则。
- 同时修改 `trr-analysis-section`、`fusion-analysis-section`、`mushra-subsection`，避免只在单一总规范中抽象约束而遗漏具体章节。
- 理由：现有规范是按章节能力组织，直接在能力层施加约束更可执行。

### 决策 3：对不可复现数字采用“三态处置”

- `Retain`：有直接证据链，保留量化数字。
- `Downgrade`：方向正确但无可复现量化，改为定性表述。
- `Remove/Future`：依赖缺失工件或冲突严重，移除并在 Limitations/Future Work 说明。

- 理由：比“全删”更保留贡献，也比“硬留”更符合不造假原则。

### 决策 4：固定指标命名与尺度声明

- 对同名指标必须给出唯一操作定义；若确属不同定义，必须改名并显式声明不可横向比较。
- 每张主表的 caption 必须包含样本数与数据来源。
- 理由：解决评审最常见疑点（定义漂移、数字不可比）。

### 决策 5：对 MUSHRA 明确“清洗口径”

- 统计结果必须基于去除误入表头行后的评分数据，并与 `results_report.md` 一致。
- 理由：原始 CSV 包含非评分行，若不声明清洗会导致可复算歧义。

## 风险 / 权衡

- [风险] 删除不可复现数字后，某些段落“显著提升”叙事力度下降
  - 缓解：用可复现结果替代，并在 Limitations 中诚实界定边界。

- [风险] 章节间改动较多，可能引入新的交叉引用错误（表号/图号）
  - 缓解：在任务中加入“全文交叉引用一致性检查”。

- [风险] 现有 capability 规范与本变更可能短期并存冲突
  - 缓解：在本次变更的增量 spec 中用“修改需求”覆盖旧口径，并在归档时同步主规范。

- [权衡] 不重跑实验保证流程稳定，但牺牲了“补全所有量化 claims”的机会
  - 处理：把无法保留的量化结论显式转入 Future Work。

## Migration Plan

1. 先完成 OpenSpec 增量规范（新增证据追溯能力 + 修改 TRR/Fusion/MUSHRA）。
2. 再按任务清单逐段修订 `Paper/content.tex` 与 `Paper/supplementary.tex`。
3. 执行文稿级核对：
   - 数据规模一致性（总数、子集、KB）；
   - 指标命名与尺度一致性；
   - 表格/图注的数据来源可定位性；
   - 主文与 supplementary 的 layer sweep 一致性。
4. 若发现任何新冲突，优先应用“三态处置”而非补造新数字。

**回滚策略**
- 文档级变更可通过 git revert 到本变更前状态；
- 规范级回滚按 capability 文件粒度进行，不影响运行时代码。
