## 上下文

Audio-Agent 目前采用多模态 RAG 架构，核心是 TRR (Texture Resonance Retrieval) 检索。目前的系统是无状态的（Stateless）：每次查询仅依赖静态知识库（ChromaDB 中的 `music_knowledge` 集合）。然而，在实际音乐制作中，用户通常需要多次尝试和微调。如果系统能“记住”用户满意的微调结果，下一次类似请求就能直接返回个性化参数，从而大幅缩短交互路径。

## 目标 / 非目标

**目标：**
- 实现 **TAM (Texture-Aware Memory)**：一个持久化的用户偏好数据库。
- 实现 **闭环学习机制**：模拟用户微调行为，并将其作为反馈存入 TAM。
- 实现 **自动化个性化评估**：通过伪用户模拟，量化记忆模块带来的收敛性提升。
- 产生 **科研图表**：展示 L2 距离随交互轮数下降的曲线图。

**非目标：**
- 不涉及真实用户的在线招募或前端 UI 开发。
- 不修改底层的 Wav2Vec2 特征提取模型。
- 不处理多用户并发冲突（假设单用户本地环境）。

## 决策

### 决策 1：记忆索引协议 (Indexing Protocol)
使用 **TRR (Gram Matrix) 向量** 作为主索引，辅以文本语义向量。
- **理由**：调研显示，二阶统计特征比一阶均值池化更能捕捉音频控制偏好。
- **替代方案**：只用文本索引。缺点是无法处理“我想找回那个有点哑（Muffled）但很厚实的音色”这种难以言表的感官记忆。

### 决策 2：检索排序策略 (Ranking Strategy)
采用 **Memory-First** 策略：在检索时，如果 Memory 中存在与当前输入 TRR 相似度 > 0.95 的记录，将其置顶。
- **理由**：用户个人的微调历史比通用预设具有更高的优先级。

### 3. 实验仿真方法 (Simulation Method)
使用 **伪用户反馈函数 (Pseudo-feedback Function)**。
- **定义**：$	heta_{corrected} = \alpha 	heta_{retrieved} + (1-\alpha) 	heta_{target}$，模拟用户将检索结果向其理想值移动的过程。
- **理由**：这是会话式 AI 领域（Conversational AI）公认的模拟人类交互的方法，成本低且可控。

## 风险 / 权衡

- **[风险] 记忆过载导致检索变慢** → **[缓解]** TAM 集合规模较小（预计 < 1000 条），ChromaDB 的 HNSW 索引足以支撑毫秒级响应。
- **[风险] 错误反馈的污染** → **[缓解]** 在仿真脚本中设定阈值，仅保存导致 L2 距离下降的“改进”作为记忆。
- **[权衡] 个性化 vs. 泛化** → **[说明]** 优先保证在相似纹理下的个性化性能，泛化性由 LLM 在检索结果基础上的二次推理来保证。
