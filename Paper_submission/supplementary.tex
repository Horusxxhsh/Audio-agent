\section{Canonical Evidence Sources and Metric Notes}

This supplementary package is synchronized to the repository's canonical experimental artifacts and the E9 derived evidence package used by the main manuscript. The primary objective evidence consists of the Protocol-A split audit, unified Protocol-A top-1 retrieval, Protocol-B exemplar-preserving projection, CLAP-covered shared-subset analysis, near-duplicate sensitivity, hard-split sweep, EPR sensitivity, and EPR validity/repair audits on the same 204-query test split. We include the listening-study report as complementary subjective evidence. We do not use legacy comparison exports as formal evidence in this revision.

All objective metrics follow the same operational definitions used in the main paper. \textbf{Norm.L2} is RMSE over flattened numeric parameter leaves after plugin-range normalization; \textbf{Norm.Acc@0.1} measures the fraction of normalized numeric leaves within an absolute tolerance of 0.1; \textbf{Recall} measures retrieval over active numeric parameters; \textbf{Cosine} is cosine similarity in the flattened parameter space; and \textbf{SwitchF1} is the value-aware active-switch F1. The earlier key-presence \textbf{Module} Jaccard is retained only in JSON audits because it can reward complete-schema outputs without verifying switch values. Missing numeric keys are treated as zeros and non-numeric leaves are ignored. Accordingly, absolute magnitudes should be interpreted \emph{within} each stated protocol rather than as perceptual distances.

\section{TRR Mechanism Ablations}

Wav2Vec uses first-order mean pooling, whereas TRR uses projected frame activations followed by Gram-matrix second-order statistics and L2 normalization. Table~\ref{tab:trr_backbone_control} isolates this comparison from the broader external-baseline matrix.

The mechanism result supports three bounded claims. First, Gram aggregation is not merely a Wav2Vec2-backbone effect: the same-layer Gram variants improve normalized distance over same-backbone mean pooling. Second, normalization is important; removing L2 normalization produces the weakest row in the table. Third, architectural choices remain meaningful: layer~5 and $d=32$/$d=64$ projected multi-layer variants trade off different metrics, so the paper should not claim that the reported TRR configuration is globally optimal. The generated artifact also records top-3 and top-5 oracle-best normalized L2 within each retrieval list, which we use only as a top-$K$ sensitivity diagnostic rather than as the deployed top-1 metric. We therefore frame TRR as a useful texture-aware retrieval prior rather than as a fully optimized representation family.
